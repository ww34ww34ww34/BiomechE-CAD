## 0. Purpose

Mature orthotic CAD systems expose reusable design knowledge through templates, histories, standard adjustments, macros and repeatable correction workflows.

BiomechE-CAD therefore treats reusable workflow knowledge as:

```text
P0 semantic infrastructure
+
P1 advanced authoring/automation UX
```

P0 does **not** mean automatic diagnosis or hidden clinical prescription. It means a workflow can be named, versioned, inspected, previewed, overridden and reproduced.

---

# 1. Definitions

## WFLOW-001 — Preset

A `PresetDefinition` configures one semantic operation or one tightly-coupled operation family.

Example:

```text
PresetDefinition
  id
  version
  contentHash
  displayName
  targetOperationType
  defaultParameters
  parameterConstraints
  compatibilityRules
  evidenceRefs[]?
```

## WFLOW-002 — Macro / workflow definition

A `WorkflowDefinition` is an ordered, versioned expansion into multiple semantic operations and optional review/inspection steps.

```text
WorkflowDefinition
  id
  version
  contentHash
  displayName
  description?
  intendedContext?
  compatibilityRules
  inputs[]
  steps[]
  dependencies[]
  mirrorPolicy
  evidenceRefs[]?
  author/provenance
```

The terms `macro`, `history`, `workflow preset` or similar vendor vocabulary may map to this one BiomechE-CAD concept.

## WFLOW-003 — Workflow instance

Applying a definition creates a project-owned instance/expansion.

```text
WorkflowApplication
  applicationId
  sourceWorkflowRef
  appliedAt
  appliedBy
  inputBindings
  parameterOverrides[]
  expandedOperationIds[]
  reviewState
  warnings[]
```

A committed revision stores enough information to reproduce the exact historical expansion.

# 2. Versioning and historical reproducibility

## WFLOW-004 — Exact version/hash

A committed design SHALL NOT reference `latest` workflow/preset semantics.

It resolves an exact:

```text
id
version
contentHash
snapshot or immutable registry reference
```

## WFLOW-005 — Later library edits do not rewrite history

Editing a library macro creates a new definition version.

Historical revisions continue to reference the old version/snapshot.

## WFLOW-006 — Expanded semantic operations survive

A committed `DesignRevision` SHALL preserve the actual expanded semantic operations generated by a workflow, not only the macro name.

Therefore even if the macro implementation becomes unavailable, the historical operation meaning remains inspectable.

# 3. Inputs and parameter binding

## WFLOW-007 — Typed input binding

Workflow inputs SHALL be typed.

Examples:

```text
SIDE
SCAN_ACQUISITION_REF
LANDMARK_SET_REF
PRESSURE_ACQUISITION_REF
ROI_REF
MATERIAL_PROFILE_REF
MANUFACTURING_PROFILE_REF
QUANTITY_MM
ANGLE_DEG
NORMALIZED_VALUE
BOOLEAN / ENUM
```

An untyped free-form value must not silently substitute for a required typed physical parameter.

## WFLOW-008 — Default != evidence threshold

A default parameter SHALL identify its governance class through the numerical registry.

Possible classes:

```text
UI_CONVENIENCE_DEFAULT
PRODUCT_DEFAULT
PROFILE_DEFAULT
EVIDENCE_CONSTRAINED_RULE
QUALIFIED_PROCESS_VALUE
```

A vendor-style convenience default must not be presented as a clinical optimum.

## WFLOW-009 — Overrides are explicit

When an operator changes a macro-generated value, the project SHALL retain:

```text
step/parameter
original default/resolved value
final overridden value
author
time
optional rationale
```

The system must never hide manual overrides behind the original macro name.

## WFLOW-010 — Dependencies are explicit

If step B depends on a value or result from step A, the dependency SHALL be declared rather than relying on invisible UI ordering.

# 4. Step model

## WFLOW-011 — Allowed P0 step classes

A P0 workflow may contain:

```text
AUTHORING_OPERATION
APPLY_PRESET
BIND_REFERENCE
MEASURE / INSPECT
QUALITY_GATE
REVIEW_REQUIRED
ANNOTATION / RATIONALE
```

P1 may later add conditional branches, suggestions or optimization loops.

## WFLOW-012 — Authoring steps expand to domain operations

An authoring step resolves to operation types governed by `16_geometry_authoring_contract.md`.

The macro layer SHALL NOT invent a parallel hidden geometry language.

## WFLOW-013 — Inspection steps do not mutate silently

A measurement/inspection step may inform later work, but it does not modify geometry unless an explicit subsequent authoring step consumes it.

## WFLOW-014 — Quality gates are visible

A workflow quality gate SHALL produce an explicit state:

```text
PASS
PASS_WITH_WARNINGS
FAIL
NOT_EVALUATED
UNAVAILABLE
```

No failed gate may be converted into a successful commit by omission.

# 5. Clinical safety and human authority

## WFLOW-015 — No hidden auto-diagnosis

Selecting/applying a workflow does not assert a diagnosis.

Profile attachment and confirmation semantics remain governed by `13_use_case_profiles.md` and Project Schema.

## WFLOW-016 — Suggestions remain suggestions

If a future module suggests a macro/preset from BiomechE results, the suggestion SHALL remain distinguishable from:

```text
USER_SELECTED
USER_CONFIRMED
IMPORTED
AUTOMATICALLY_APPLIED
```

P0 SHALL NOT silently turn an algorithmic suggestion into a committed clinical prescription.

## WFLOW-017 — High-impact steps may require review

A workflow definition may mark steps:

```text
AUTO_PREVIEW
REVIEW_BEFORE_COMMIT
MANDATORY_CONFIRMATION
```

The required review policy is part of the workflow version.

---

# 6. Bilateral/mirror behavior

## WFLOW-018 — Workflow mirror policy

A workflow SHALL declare:

```text
MIRROR_SAFE_AUTOMATIC
MIRROR_WITH_STEP_TRANSFORMS
MIRROR_REQUIRES_REVIEW
NOT_MIRRORABLE
```

## WFLOW-019 — Step-level mirror transform

Each generated geometry operation follows the operation-specific mirror rules in the Geometry Authoring Contract.

A workflow may not claim mirror safety if any mandatory child step is `NOT_MIRRORABLE`.

## WFLOW-020 — Bilateral independence after application

A macro applied to both sides produces distinct side-owned operations/revisions. Later editing on LEFT must not mutate RIGHT.

---

# 7. Compatibility and context

## WFLOW-021 — Compatibility is explicit

A definition may constrain:

```text
orthosis/template family
side support
capture type / weight-bearing state
required landmark set
required pressure/BiomechE capability
indication/evidence profile
material/manufacturing profile
minimum software/algorithm capability
```

## WFLOW-022 — Unsupported context is not silently coerced

Application state may be:

```text
COMPATIBLE
COMPATIBLE_WITH_WARNINGS
INCOMPATIBLE
INSUFFICIENT_CONTEXT
```

If required context is missing, the operator may resolve it explicitly or choose another workflow; the system must not fabricate compatibility.

---

# 8. Determinism

## WFLOW-023 — Deterministic expansion

Given the same exact workflow version, input bindings, defaults/registry versions and algorithm versions, the semantic expansion SHALL be deterministic.

## WFLOW-024 — Dynamic external `latest` is forbidden during committed expansion

If a workflow uses external definitions, the committed expansion resolves exact versions/snapshots.

## WFLOW-025 — Re-execution creates a new application/revision

Re-running a workflow after source data, algorithms or profiles change creates a new application/result/revision. It does not overwrite history.

---

# 9. Minimum P0 workflows the product model must support

The P0 infrastructure SHALL be sufficient to represent, without hardcoding vendor-specific UI:

```text
A. base template + size + outline initialization
B. arch + heel + wedge prescription sequence
C. pressure-guided offload feature placement + inspection
D. bilateral source -> mirrored contralateral starting point -> independent review
E. scan-conform + manual refinement + inspection
F. production preparation + minimum-thickness / DFM inspection
G. saved user/clinic best-practice workflow with explicit overrides
```

These are semantic capability examples, not mandatory automatic one-click clinical routines.

# 11. Schema evolution note

The current Project Schema already contains `presetDefinitions[]`, `sourcePresetRef` and immutable definition rules.

A future schema revision should materialize the workflow concepts defined here, likely by adding:

```text
workflowDefinitions[]
sourceWorkflowRef?
WorkflowApplication / expansion provenance
parameter override records
```

Do not modify schema v0.1 or fixture serialization opportunistically merely to make this document appear implemented. Schema evolution must be explicit and migratable.

The documentation review confirms the v1 contract:

1. single-operation preset and multi-operation workflow semantics are distinct;
2. exact version/hash and historical expansion are preserved;
3. typed inputs, default governance, dependencies and overrides are explicit;
