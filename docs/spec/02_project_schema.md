# BiomechE-CAD — Project Schema v0

**Status:** ACTIVE / SCHEMA BASELINE v0  
**Date:** 2026-08-14  
**Architecture:** geometry-kernel and storage-engine independent  
**Functional authority:** `docs/spec/BIOMECHE_CAD_FUNCTIONAL_SPEC_V2.md`  
**Bibliographic authority:** `docs/BIBLIOGRAPHY.md`

---

## 0. Purpose

This document defines the **logical persisted project contract** for BiomechE-CAD.

It answers:

```text
what must have an identity?
what is mutable vs immutable?
what must be versioned?
what must retain source/provenance?
what references what?
what must survive export/import/migration?
```

It deliberately does **not** select:

```text
database technology
object-relational mapper
geometry kernel
native-vs-WASM runtime
final project-package container
cloud synchronization technology
```

The same logical schema must be usable by desktop, web/server and future mobile deployments.

---

# 1. Design principles

## SCHEMA-PRINC-001 — Semantic design is authoritative

For native BiomechE-CAD projects, the authoritative design state is the versioned semantic prescription/operation model, not a final STL or tessellated mesh.

Derived geometry may be cached and hashed, but a cache is not allowed to erase:

```text
feature type
clinical/anatomical semantics
dose
units
placement/reference
material/mechanical prescription
source evidence
algorithm version
```

Legacy imported projects may explicitly use `IMPORTED_GEOMETRY` authority mode when reconstructable semantic operations do not exist.

## SCHEMA-PRINC-002 — Revisions are immutable snapshots

A committed `DesignRevision` is immutable.

A later edit creates a new revision with explicit parent linkage.

```text
revision A
   ↓
revision B
   ↓
revision C
```

P0 may expose a linear history in the UI, but the schema permits `parentRevisionIds[]` so future branch/merge workflows do not require a breaking schema redesign.

## SCHEMA-PRINC-003 — Definitions used by a revision are frozen by reference

A project may use reusable definitions such as:

```text
BaseTemplate
IndicationProfile
MaterialDefinition
PROMInstrumentDefinition
ManufacturingProfile
PresetDefinition
```

A committed revision SHALL reference the **exact definition revision** used.

If the definition lives in an external/global registry, the project SHALL retain enough information to reproduce the historical meaning:

```text
id
revision/version
content hash
source URI/registry [optional]
embedded snapshot or resolvable immutable snapshot
```

A pointer to `latest` is never sufficient for a committed clinical/manufacturing revision.

## SCHEMA-PRINC-004 — Raw evidence is immutable

Original acquisitions and imported source files are preserved as immutable assets.

Corrections such as alignment, cropping, filtering, ROI definition or registration create derived objects and provenance records; they do not overwrite the original bytes under the same asset identity.

## SCHEMA-PRINC-005 — Measured, nominal, modeled and predicted remain separate

The schema SHALL distinguish:

```text
supplier nominal property
measured material property
measured physical-part property
modeled/effective property
measured biomechanical outcome
predicted biomechanical outcome
CAD nominal geometry
manufactured measured geometry
```

## SCHEMA-PRINC-006 — The physical copy has its own identity

Two orthoses manufactured from the same `DesignRevision` remain different `PhysicalOrthosis` entities if produced in different runs/lots or issued at different times.

## SCHEMA-PRINC-007 — Provenance is a graph

The project lineage is conceptually compatible with the W3C PROV pattern:

```text
Entity
  used/generated by
Activity
  associated with
Agent
```

[STD-W3C-PROV-O-2013]

BiomechE-CAD does not need RDF internally, but its provenance model SHALL retain enough structure to answer:

```text
what was generated?
from what inputs?
by what operation/process?
by whom/what software/device?
when?
using which algorithm/profile/version?
```

## SCHEMA-PRINC-008 — External interoperability does not dictate the internal model

FHIR mappings may be provided for patient identifiers, observations, questionnaire responses and provenance, but BiomechE-CAD SHALL NOT store arbitrary FHIR resources as its internal project model merely to gain interoperability.

FHIR `Observation`, `QuestionnaireResponse` and `Provenance` are mapping targets/bridges, not the canonical authoring model [STD-HL7-FHIR-R5-OBSERVATION; STD-HL7-FHIR-R5-QUESTIONNAIRE; STD-HL7-FHIR-R5-PROVENANCE].

# 2. Reference serialization contract

## 2.1 Logical schema vs reference serialization

The logical schema is implementation-neutral.

For portable validation and test fixtures, the **reference serialization** SHALL be UTF-8 JSON and SHALL be describable with JSON Schema Draft 2020-12 [STD-JSON-SCHEMA-2020-12].

This does not require the runtime database itself to be JSON/document-oriented.

## 2.2 Project schema identifier

```text
schemaId      = "biomeche-cad-project"
schemaVersion = "0.1"
```

Version semantics are project-defined:

```text
major change  -> migration may be non-trivial / incompatible
minor change  -> backward-compatible additive evolution where possible
```

Do not infer compatibility only from the numeric string; migration code declares supported source/target versions explicitly.

## 2.3 IDs

Internal persistent IDs SHOULD use UUIDs conforming to RFC 9562 [STD-RFC-9562].

Preferred generated form:

```text
UUIDv7
```

because it provides globally unique IDs with time-ordered characteristics useful for local/offline creation and logs.

Rules:

1. IDs are opaque to business logic.
2. Never derive clinical semantics from ID contents.
3. Imported/external business identifiers remain in `externalIdentifiers[]` and SHALL NOT replace the internal entity ID.
4. An ID is never reused for a semantically different entity.

## 2.4 Timestamps

Persisted event timestamps SHALL use RFC 3339 offset-aware date-time strings [STD-RFC-3339].

Example:

```text
2026-08-14T18:29:00+02:00
```

For chronology/integrity calculations the implementation may normalize to UTC, but the schema may additionally preserve original timezone/location context where clinically or operationally relevant.

## 2.5 Hashes

All binary/raw/generated assets that enter provenance SHALL support an algorithm-tagged digest:

```text
HashValue
  algorithm: "sha256"
  value: lowercase hex or base64url according to project convention
```

SHA-256 is the P0 baseline secure hash algorithm [STD-NIST-FIPS-180-4].

The algorithm name is persisted so a later migration can introduce another hash without ambiguity.

## 2.6 Canonical JSON hashing

When a hash of JSON metadata itself is required, the implementation SHOULD use a named canonicalization method rather than hashing arbitrary pretty-printed JSON.

P0 recommended method:

```text
JCS / RFC 8785
```

[STD-RFC-8785]

Binary assets are hashed over their raw bytes; JCS applies only to JSON metadata selected for canonical hashing.

# 3. Common primitives

## 3.1 `EntityMeta`

Every first-class persisted entity SHOULD carry:

```text

  id: UUID/string
  createdAt: RFC3339 timestamp
  createdBy?: AgentRef
  sourceSystem?: string
  extensions?: object
```

Versioned entities additionally carry their own `revision` / `version` field.

## 3.2 `ExternalIdentifier`

```text

  system: URI/string

  issuer?: string
```

```text

  id
  version
```

# 4. Asset model

Large/binary payloads SHALL not be duplicated inline throughout the manifest.

```text
AssetDescriptor
  assetId
  role
  mediaType
  byteLength
  hash: HashValue

  originalFileName?
  originalSourceUri?
  storageRef

  createdAt
  sourceAssetIds[]?
  provenanceRecordId?

  availability
    EMBEDDED
    LOCAL_EXTERNAL
    REMOTE_EXTERNAL
    MISSING
```

Typical roles:

```text
RAW_PRESSURE
RAW_SCAN3D
RAW_IMAGE2D
CALIBRATION
DERIVED_PRESSURE
ROI_MASK
DERIVED_MESH
MANUFACTURING_BODY
STL
3MF
GCODE
CNC_TOOLPATH
PROM_RAW_RESPONSE
REPORT_PDF
LOG
QC_DATA
DEVIATION_MAP
OTHER
```

### Asset invariants

- `assetId` identifies the logical asset record.
- `hash` identifies its bytes.
- Replacing bytes requires a new hash and normally a new asset record.
- A project package SHALL never claim an asset is embedded when its bytes/hash cannot be verified.


`AdherenceMeasurement` preserves both method and denominator; e.g. `hours/day`, `% weight-bearing time` and `% steps with device` remain different metrics.

# 21. Provenance record

## 21.1 W3C-inspired lightweight structure

```text
ProvenanceRecord
  provenanceId
  activityType

  inputEntityRefs[]
  outputEntityRefs[]

  startedAt?
  endedAt?
  recordedAt

  agentRefs[]
  softwareBuildRefs[]
  deviceRefs[]?

  algorithmRefs[]?
  profileRefs[]?
  evidenceRefs[]?

  rationale?
  warnings[]?
```

This intentionally maps cleanly to the W3C `Entity / Activity / Agent` mental model [STD-W3C-PROV-O-2013].

FHIR Provenance likewise emphasizes version-specific targets and the agents/entities involved in creating or revising information; this is a useful external mapping target [STD-HL7-FHIR-R5-PROVENANCE].

## 21.2 Provenance vs audit

```text
ProvenanceRecord
  = why/how an entity was derived/generated

AuditEvent
  = what application/security/user event occurred
```

They can overlap but SHALL not be conflated.

5. Legacy imports preserve original source assets and source version when known.

# 24. Extension mechanism

All extensibility SHALL be explicit.

Preferred pattern:

```text
extensions
  namespace/key -> structured value
```

Rules:

- extensions cannot override core required semantics;
- unknown extension namespaces may be preserved round-trip even if not interpreted;
- a P0 safety/clinical/manufacturing field SHALL NOT be hidden only inside a vendor extension;
- extension promotion into the core schema requires a schema-version change and migration rule.

# 25. Package / container independence

The logical project package consists of:

```text

+ immutable assets
+ optional embedded definition snapshots
+ optional reports/export artifacts
```

The physical container remains intentionally OPEN.

Possible realizations include:

```text
directory
ZIP-like archive
local database + export package
object store
server document graph
```

All must be able to emit/consume the same logical manifest contract.

A future extension such as `.biomechecad` SHALL therefore be a packaging decision, not a rewrite of the domain schema.

# 26. Privacy / minimum-necessary export

The schema SHALL support creating derived export packages that do not require full patient demographics.

At least three policy modes should be representable:

```text
FULL_CLINICAL
PSEUDONYMIZED
MANUFACTURING_MINIMUM
```

`MANUFACTURING_MINIMUM` should normally contain only identifiers and clinical details required to safely manufacture/trace the prescribed part under the deployment policy.

Privacy/security policy itself is deployment/regulatory scope and is not fully specified here.

# 27. Optional FHIR interoperability map — P1

BiomechE-CAD remains internally domain-specific, but the schema intentionally permits controlled external mapping.

Indicative map:

| BiomechE-CAD | FHIR R5 concept |
|---|---|
| `PatientLink.externalIdentifiers` | Patient Identifier / external patient reference |
| quantitative point-in-time outcome | `Observation` |
| PROM instrument + response | `Questionnaire` + `QuestionnaireResponse` |
| derivation/version activity | `Provenance` |
| device/source metadata | Device / Observation device references as applicable |

FHIR `Observation` is intended for measured/simple assertions and explicitly distinguishes itself from questionnaire-answer capture; `QuestionnaireResponse` retains the questionnaire definition/answer structure [STD-HL7-FHIR-R5-OBSERVATION; STD-HL7-FHIR-R5-QUESTIONNAIRE].

No FHIR mapping is allowed to discard BiomechE-CAD-specific revision, ROI, material or manufacturing semantics merely because the target resource is less expressive.

# 29. P0 schema invariants / acceptance semantics

## `SCHEMA-001` — project round-trip

Serialize → parse → serialize preserves all normative semantic values and references.

## `SCHEMA-002` — unique IDs

No two first-class entities in the same project share the same `(entityType,id)` identity unless explicitly the same entity representation.

## `SCHEMA-003` — no dangling required references

Every required local reference resolves to exactly one entity or explicitly records an external immutable dependency.

## `SCHEMA-004` — immutable revision

A committed revision cannot change content under the same `revisionId/contentHash`.

## `SCHEMA-005` — revision DAG

`parentRevisionIds` contains no cycle.

## `SCHEMA-006` — exact-definition resolution

A committed revision can resolve the exact template/profile/material/PROM/manufacturing definition versions it used.

## `SCHEMA-007` — raw asset integrity

Raw acquisition asset bytes match the stored hash.

## `SCHEMA-008` — timestamp validity

Normative timestamps parse as RFC 3339 and identify an offset/UTC relationship.

## `SCHEMA-009` — unit preservation

All physical quantities round-trip with units; no naked numeric physical dose is allowed where the sub-spec requires a quantity.

## `SCHEMA-010` — side consistency

Left/right entity references do not silently cross sides unless the operation explicitly represents a mirror/cross-side relation.

## `SCHEMA-011` — registration direction

Every transform names source and target frames.

## `SCHEMA-012` — ROI version integrity

Outcome metrics/targets identify the ROI version used.

## `SCHEMA-013` — measured/predicted separation

A predicted result cannot deserialize as a measured result without explicit migration/conversion error.

## `SCHEMA-014` — outcome revision linkage

Every outcome intended to evaluate an orthosis identifies the exact design revision and, when applicable, physical part/manufacturing context.

## `SCHEMA-015` — profile target provenance

Every evidence-derived target retains profile/version and evidence reference/locator.

## `SCHEMA-016` — PROM historical reproducibility

PROM measurement resolves exact instrument version/language/scoring algorithm version.

## `SCHEMA-017` — material property source

Nominal, coupon, final-part and service-state properties cannot collapse into an untyped `propertyValue`.

## `SCHEMA-018` — manufacturing lineage

`PhysicalOrthosis` resolves:

```text
DesignRevision
→ ManufacturingProfile revision
→ ManufacturingRun
→ ManufacturingArtifact
→ material lot(s)
```

## `SCHEMA-019` — physical copy uniqueness

Two manufacturing runs can create distinct physical parts from the same design without ID collision.

## `SCHEMA-020` — blocking QC guard

A qualified profile with failed/missing blocking QC cannot serialize a physical part as validated `ACCEPTED`.

## `SCHEMA-021` — service history append-only

A new service observation creates a new `ServiceState`; historical states remain addressable.

## `SCHEMA-022` — evidence reference integrity

Project evidence references use stable bibliography IDs and optional truthful locators; evidence text is not silently rewritten as a new source.

## `SCHEMA-023` — migration trace

A schema migration records source/target version and any known information loss/warnings.

## `SCHEMA-024` — package asset verification

An embedded asset marked available validates against its stored digest.

## `SCHEMA-025` — external identifier separation

External/business IDs are not substituted for internal entity IDs during round-trip/import.

## `SCHEMA-026` — operation algorithm version

Every geometry/design operation that changes authoritative design state resolves an `AlgorithmRef`.

## `SCHEMA-027` — provenance input/output trace

A derived acquisition/design/manufacturing artifact can identify the input entity/entities and activity that generated it.

## `SCHEMA-028` — privacy-profile export

A pseudonymized/manufacturing-minimum export can omit full demographics without breaking design/manufacturing lineage.
